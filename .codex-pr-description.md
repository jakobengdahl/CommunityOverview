## Summary

Record one `nodes_added` / `nodes_removed` activity entry per actual membership
change applied directly by the server: server-handled UI operations, MCP
`add_nodes_to_session` / `remove_nodes_from_session`, additive MCP
`add_to_visualization` results applied to stored shared sessions, and
server-applied clears. No-op repeats and browser echoes produce no extra entry.
Server additive pushes and clears preserve order behind an in-flight op batch.

Membership has an independent 500-record retention budget and the same seven-day
age limit, so it cannot displace undoable records. Each record stores a total
count and at most `MAX_ACTIVITY_NODE_IDS` (100) distinct IDs, without snapshots,
forward operations or inverses. User operations retain the caller's presence
identity; MCP operations display “via MCP”. The shared MCP identity does not
identify an individual MCP caller. Membership does not invalidate redo history.
English and Swedish activity descriptions include the total count.

## What was not changed (scope)

Browser-applied membership is deferred to a follow-up: `load_visualization` /
`get_saved_view` and replacement pushes, browser `computeOps` membership sync,
and session auto-add agent pushes. Those pushes do not change server membership
before delivery, and their later browser membership sync records nothing.
Additions arriving by saved-view load or client-side sync are a documented known
gap. A browser canvas diff cannot reliably identify the originating action;
recording it now would imply attribution this PR cannot guarantee. Other activity
kinds in the same browser batch continue to be recorded.

No hydration changes remain in this PR. The existing `nodes_added` hydration in
`App.jsx` can restore a node after a later clear/remove while its node-details
request is in flight. This race already exists on main: the removed race test
was run against the unchanged main-version `App.jsx` and `sessionSyncClient.js`
and reproduced the stale node after clear. It is deliberately left for the
browser-sync follow-up, as requested. Legacy-only channels remain client-applied.
Node membership remains non-undoable because removal also changes group state.
