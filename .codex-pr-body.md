## Summary

Shared context agents need to collaborate inside one session (re-scoped task):

1. **Session purpose.** `Session.description` (string | null, ≤ 4000 chars) is persisted with the session document, listed in the meta index, and returned on the MCP session resource (`get`/`list`/`create`) and the REST session payload. It is set or cleared by the new `describe_visualization_session` MCP tool, which emits a sequenced `session_described` state op (last write wins, get-or-create, own rate-limit key, `LayoutBusy` guard), the same way rename does. Because it is session metadata, not canvas state, `clear_visualization` keeps it. Both rollback paths in `SessionManager` restore it when a persist fails.
2. **Per-op attribution for node changes.** `nodes_added` / `nodes_removed` now write record-only activity entries (`RECORDED_ONLY_OPS`, no inverse, never undoable) naming the `actor` and only the ids that actually changed, so `get_session_activity` / `GET …/activity` answer "who added / removed this node". Moves and layouts were already attributed. The web Activity drawer gets the matching `history.desc.nodes_added/removed` strings (en + sv) so the new entries don't show as "unknown".

Docs: `MCP_SESSION_LIFECYCLE_CONTRACT.md` (§2 field, §3 operation), `MULTI_USER_SESSIONS_DESIGN.md` (§3.1 shape, op catalogue), `backend/DEVELOPMENT.md` (MCP table, activity endpoint), `docs/USER_GUIDE.md` §5.2.

**Security impact:** No new auth surface. The new tool goes through the same `_authorize_session(GRAPH_ACTION_MUTATE, …)` gate and per-tool MCP rate bucket as rename. The description is bounded (4000 chars) and type-checked at the op boundary. The new activity entries carry the same `actor` as the existing records, so they are retained for 500 records / 7 days and covered by `SessionStore.erase_actor`. No new identity data is stored outside the activity log. This is not a permission model.

## What was not changed (scope)

- **Participant history** (item 3) is not implemented. Presence is ephemeral by design (§3.3), and persisting participant identities needs an owner decision. The activity log now answers "who touched this node last" for add, remove, move and layout.
- No REST write path for the description (only MCP), and no web UI to show or edit it yet. The REST payload already returns it.
- Trade-off: node add/remove records count toward the 500-record activity cap. A session with many adds evicts older undo history sooner. Only ids that actually changed are recorded, and each op writes at most one record.
- Test volume: `test_session_activity.py` and `test_session_manager.py` were already past the 1.5x per-file ratio on `main`. This PR adds about 20 lines and 3 lines to them (information only, per the rule).
