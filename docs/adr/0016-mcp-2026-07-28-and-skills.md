# ADR 0016 — MCP 2026-07-28 and skills in three layers

- **Status:** Accepted
- **Date:** 2026-11-26
- **Scope:** Open-source core

## Context

The MCP server currently depends on `mcp>=1.29.1,<2` and uses `FastMCP`.
It builds instructions from the loaded schema and presentation when the server
is constructed. The configuration loader normally reads the schema once into a
singleton; an explicit reload exists, but does not rebuild those instructions
([server](../../backend/api_host/server.py), [instructions](../../backend/api_host/mcp_mount.py),
[loader](../../backend/config/config_loader.py)). The gateway forwards
`Mcp-Session-Id` in both directions for Streamable HTTP
([proxy](../../services/mcp_oauth_gateway/proxy.py)). Attachment tools carry text
or base64 in model context, with a configurable decoded-size limit capped at
3,000,000 bytes; attachment storage itself has separate limits
([tools](../../backend/service/attachment_tools.py),
[storage](../../backend/core/attachment_store.py)). `create_skill` creates
reusable Skill nodes with content and when-to-use instructions
([system nodes](../../backend/service/system_nodes.py)).

The [2026-07-28 MCP specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
was released as final. Python [mcp 2.x](https://pypi.org/project/mcp/) is stable;
its [v2 release notes](https://github.com/modelcontextprotocol/python-sdk/releases)
rename FastMCP to `MCPServer` and describe the extension API and
`subscriptions/listen`. Its [subscription bus](https://github.com/modelcontextprotocol/python-sdk/blob/main/src/mcp/server/mcpserver/server.py)
can use a pluggable backend. The extension framework is specified in
[SEP-2133](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-05-21-mcp-2026-07-28-rc.md).

The decision assumed Python mcp had no built-in skills. That is not true of the
SDK's main branch: [skills protocol support was merged](https://github.com/modelcontextprotocol/python-sdk/pull/3485),
although the merged change leaves discovery, indexing and refresh policy to a
provider. Whether a published 2.x package includes that support is, as of
2026-11-26, unverified. This discrepancy does not change the decision below.

The [skills extension beta specification](https://github.com/modelcontextprotocol/ext-skills/blob/main/specification/beta/skills.mdx)
implements [SEP-2640](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2640-skills-extension.md),
which is Final. It defines `io.modelcontextprotocol/skills`, `skills/list` and
`skills/get`, conventional `skill://` resource URIs, per-file SHA-256 digests,
and `ttlMs` and `cacheScope` list caching hints. A changed file set or digest
revokes any persisted content-bound approval and requires a new prompt before
loading or execution. It defines no skills-specific change notification. The
claim that the TypeScript SDK sends `notifications/resources/list_changed` on
skill catalog changes is, as of 2026-11-26, unverified.

The [files extension](https://github.com/modelcontextprotocol/experimental-ext-file-uploads/blob/main/specification/draft/file-uploads.md)
`io.modelcontextprotocol/files` is experimental and its specification is a draft.
The claim that it has been experimental since 2026-11-10 is, as of 2026-11-26,
unverified.

## Decision

Adopt MCP protocol 2026-07-28, upgrading the Python SDK first. Keep skills
behind a configuration flag. Deliver graph knowledge in three layers:

1. **Working method:** a core-versioned `SKILL.md` describing how to use the
   tools. It is the same for every graph, with sections only for enabled tools.
2. **Graph semantics:** a skill generated from the profile schema, describing
   node and relationship types and their meaning.
3. **Content knowledge:** deterministic core statistics, including counts,
   distributions and cross-type patterns, exposed by a `describe_graph` tool
   and `graph://profile` resource. This is not a skill: content changes would
   change its digest and cause hosts with persisted content-bound approval to
   prompt again. An optional scheduled agent may also write a generated Skill
   node which a human can edit.

Curated Skill nodes and those agent-generated Skill nodes are served as skills.
The layer 3 tool and resource remain subject to the caller's graph access.

### Seams and updates

- `SkillProvider` supplies the core and graph-derived skills; a deployment can
  register its own provider.
- `SchemaSource` supplies the profile schema and emits a schema-changed event.
  The core recomputes instructions and schema-derived skills and signals the
  resulting changes when it receives that event.
- `SkillChangePublisher` maps catalog changes to
  `notifications/resources/list_changed`, delivered through
  `subscriptions/listen`. A future standard skills notification can replace the
  mapping. A pluggable subscription bus backend carries events across processes.
  Clients must still refresh and cannot assume every host reacts to this signal.
- Prepare an upload-target seam in attachment storage. Adopt the files extension
  only once it is stable; until then retain existing attachment paths.

Configure `ttlMs` and `cacheScope` per layer, with stable SHA-256 digests of
served skill file bytes. Put version and node revision in frontmatter metadata
where applicable. Provide an admin `refresh_skills` operation and fallback
`list_skills` and `get_skill` tools for hosts without the extension. Use standard
protocol methods and notifications; do not introduce proprietary protocol
methods. Cache hints do not replace digest verification or authorization.

### Security

Apply the same sanitisation as `SkillsLoader`: reject known prompt-injection
patterns and strip dangerous HTML elements while retaining safe markup. Limit
each skill to 512 files and 16 MiB total. Filter skills, resources, profile
statistics and fallback results using the same access rules as node reads;
use `cacheScope: private` whenever access varies between callers. Digests check
consistency, not trust in the source.

### Phasing

1. Upgrade the SDK and protocol to 2026-07-28.
2. Serve layers 1 and 2 as skills behind the flag.
3. Add the layer 3 `describe_graph` tool and `graph://profile` resource.
4. Introduce `SchemaSource` and live schema-change propagation.
5. Serve curated Skill nodes as skills, including editable generated nodes.
6. Adopt the files extension when stable, using the upload-target seam.

## Consequences

Clients get stable working instructions and schema semantics separately from
frequently changing graph statistics. Skills require host support and approval;
configuration, refresh, authorization and cache invalidation add operational
complexity. Existing clients can use fallback tools. The notification is a
resource catalog hint, not a guarantee that a host refreshes skills. SDK and
extension compatibility must be checked during implementation. This ADR changes
no runtime behavior on its own.

## Alternatives considered

- **Content knowledge as a skill:** rejected because ordinary graph changes
  rotate digests and revoke persisted approval, causing repeated prompts.
- **Dynamic skill files:** rejected because a dynamic manifest cannot bind
  persisted approval to a known file set or verify it with advertised digests.
- **A proprietary change notification:** rejected because it fragments client
  interoperability; the publisher seam allows a future standard mapping.
